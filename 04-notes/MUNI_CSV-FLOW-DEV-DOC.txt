==============================================================
  1. UEBERSICHT UND ZWECK
==============================================================

Der CSV Flow ist eine mehrstufige Python-Pipeline die ArchiMate-
Modelle, BPMN-Prozesse und XLSX-Exporte in ein einheitliches
CSV-Format konvertiert das von Archi 5.8 direkt importiert
werden kann.

Ziel ist ein deterministischer, audit-freundlicher Prozess
ohne manuelle Eingriffe zwischen den Stages.

Quellsysteme:
  - Archi (.archimate) via OEF XML Export
  - BPMN (.bpmn) via master.xml Aggregat
  - XLSX (.xlsx) via direkten Dateiimport

Ziel:
  - master CSVs (elements, relations, properties)
  - Import-Snapshot fuer Archi CSV Import

==============================================================
  4. KONFIGURATIONSDATEIEN
==============================================================

--------------------------------------------------------------
  root.txt
--------------------------------------------------------------
  Ort:    <irgendwo im Dateisystem>
  Zweck:  Definiert BLUEPRINT_ROOT absolut oder relativ

  Format:
    BLUEPRINT_ROOT=C:\Pfad\zum\Blueprint

  Regeln:
    - Genau ein BLUEPRINT_ROOT Eintrag
    - Leere Zeilen und # Zeilen werden ignoriert
    - Wird von CSV00 gefunden durch Traversal (bis 8 Ebenen)

--------------------------------------------------------------
  run-scope.txt
--------------------------------------------------------------
  Ort:    <root>/03-stages/run-scope.txt
  Zweck:  Deklarativer Lauf-Scope - definiert WAS verarbeitet wird
          Dient als Trigger und Filter fuer alle nachgelagerten Stages

  SOURCE-Typen und ihre Bedeutung:
    archi   Aktive Archi .archimate Modelle (Pruefung/Inventar)
    OEF     Vorhandene OEF XML Exporte aus Archi
    XLSX    Welche Excel Files inkludiert werden sollen
    CSV     Ob elements/properties/relations.csv vorhanden sind
    MASTER  Welche OEF Modelle fuer CSV/XML Run relevant sind
    BPMN    Welche BPMN Modelle im Flow beruecksichtigt werden

  Pair-Konvention (KRITISCH):
    SOURCE=<typ>        <- Zeile N
    MODEL=<dateiname>   <- Zeile N+1, direkt darunter, kein Abstand

  Aktives Pair:
    SOURCE=MASTER
    MODEL=Importer.xml

  Inaktives Pair (beide Zeilen mit #):
    #SOURCE=MASTER
    #MODEL=Importer.xml

  ACHTUNG - Bekannter Bug (noch nicht gefixt):
    Der run-scope Parser in CSV03/07/08/09 filtert #-Zeilen
    vor der Pair-Erkennung heraus. Das bedeutet:
    - Kommentierte Pairs koennen falsch einem anderen SOURCE
      zugeordnet werden wenn die Zeilen durch den Filter
      zusammenruecken.
    - Workaround: Keine # Kommentare in aktiven .txt Dateien
      verwenden bis der Cleaning Run durchgefuehrt wurde.

  SNAPSHOT-Block (read-only, nie aktiv):
    Zeilen mit SNAPSHOT_SOURCE= und SNAPSHOT_MODEL= sind
    reine Dokumentation und werden von keinem Script als
    aktive SOURCE/MODEL Pairs interpretiert.
    Sie beginnen alle mit # und sind daher inaktiv.

--------------------------------------------------------------
  csvmapping.txt  (CSV Flow)
--------------------------------------------------------------
  Ort:    <root>/02-artifacts/02-csv/01-mapping/csvmapping.txt
  Zweck:  Definiert WELCHE Archi-Modelle in den CSV Flow kommen
  Konsument: CSV03-resolve_run_scope.py

  Format:
    archi[model=<pattern>]-element-xsi:type="<type>"

  Muster:
    *         Wildcard (matcht alles)
    *Process* Substring-Match (case-insensitive)

  Beispiel:
    archi[model=*.*]-element-xsi:type="*"
    (alle Modelle, alle Typen)

  Hinweis: CSV03 liest NUR den model= Teil aus.
           Der element/type Teil wird ignoriert.

--------------------------------------------------------------
  csvmapping.txt  (XLSX Flow)
--------------------------------------------------------------
  Ort:    <root>/02-artifacts/03-XLSX/01-mapping/csvmapping.txt
  Zweck:  Spaltenmapping XLSX -> CSV
  Konsument: CSV07-xlsx_2_csv.py

  Format (4-spaltig, kein Header):
    "XLSX_Spaltenname","Sheetname","CSV_Spaltenname","ziel.csv"

  Beispiel:
    "Name","Elements","Name","elements.csv"

--------------------------------------------------------------
  propmapping.txt
--------------------------------------------------------------
  Ort:    <root>/02-artifacts/03-XLSX/01-mapping/propmapping.txt
  Zweck:  Spaltenmapping fuer Properties Sheet aus XLSX
  Konsument: CSV08-properties2csv.py

  Format (4-spaltig):
    "XLSX_Spalte","Sheet","CSV_Spalte","properties.csv"

  Pflichtfelder die gemapt sein muessen:
    Owner Id -> ID
    Key      -> Key
    Value    -> Value

--------------------------------------------------------------
  csvexport.txt
--------------------------------------------------------------
  Ort:    <root>/02-artifacts/02-csv/02-sync/csvexport.txt
  Zweck:  Definiert welche Element-TYPEN aus dem Import-Snapshot
          AUSGESCHLOSSEN werden
  Konsument: CSV99-export_snapshot.py

  Format:
    Eine Zeile = ein Typ (exakter String-Match, case-sensitive)
    Keine Wildcards, kein Regex

  Beispiel aktive Regel:
    ArchimateModel

  Hinweis: # Kommentare funktionieren hier korrekt weil
           CSV99 keine Pair-Logik benoetigt.

--------------------------------------------------------------
  bpmnmastercsvsync.txt
--------------------------------------------------------------
  Ort:    <root>/02-artifacts/00-xml/01-mapping/bpmnmastercsvsync.txt
  Zweck:  BPMN Element -> Archi Typ Mapping
  Konsument: CSV09-masterXml2Csv.py

  Format (5-spaltig, kein Header):
    "bpmn_tag","id_attribut","name_attribut","archi_typ","property_key"

  Spalten:
    bpmn_tag        Lokaler XML Tag (case-insensitive, namespace-agnostisch)
    id_attribut     BPMN Attribut fuer den Prozess-Identifier (meist: id)
    name_attribut   BPMN Attribut fuer den Anzeigenamen (meist: name)
    archi_typ       Ziel-ArchiMate Typ fuer neue Elemente
    property_key    Schluesselbegriff in properties.csv (z.B. BPMN_ID)

  Beispiel:
    "process","id","name","BusinessProcess","BPMN_ID"

  Erweiterbarkeit:
    Weitere Quellsysteme koennen mit eigenem property_key
    hinzugefuegt werden ohne das Script zu aendern:
    "process","ProcessID","ProcessName","BusinessProcess","SAP_ID"

==============================================================

--------------------------------------------------------------
  CSV00 - validate_environment.py
--------------------------------------------------------------
  Zweck:    Umgebung validieren, root.txt lesen, BLUEPRINT_ROOT
            aufloesen und als Artefakt persistieren.
  Input:    root.txt (durch Traversal gefunden)
  Output:   03-stages/99-logs/CSV00-root.resolved.txt
            03-stages/99-logs/CSV00-validate_environment.log
  Fehler:   Abbruch bei fehlendem root.txt, mehrdeutigem
            BLUEPRINT_ROOT oder nicht existierendem Pfad.
  Abhaeng.: Keine (erste Stage, bootstrappt alles andere)
  Besonder: Alle nachgelagerten Scripts lesen den Root aus
            CSV00-root.resolved.txt - nicht aus root.txt direkt.

--------------------------------------------------------------
  Zweck:    ArchiMate Modell-Inventar erstellen.
            Informationell, keine Entscheidungen.
  Input:    CSV00-root.resolved.txt
            01-model/00-archimate/ (Ordnerstruktur)
  Output:   03-stages/model-scope.txt
            Sektionen: ACTIVE_MODELS / ACTIVE_SUB_MODELS /
                       OTHER_ARCHIMATE_FILES
  Fehler:   Abbruch nur bei technischen Fehlern
  Besonder: Kein Erstellen von Verzeichnissen.
            Reine Inventarisierung.

--------------------------------------------------------------
  CSV02 - leer.py
--------------------------------------------------------------
  Zweck:    Platzhalter / Reserviert
  Status:   Leer, gibt nur print() aus
  Hinweis:  Fuer kuenftige Stage vorgehalten

  CSV03 - resolve_run_scope.py
--------------------------------------------------------------
  Zweck:    Entscheidungspunkt - bestimmt WELCHE Modelle
            im aktuellen Lauf verarbeitet werden.
            Liest csvmapping.txt und model-scope.txt.
            Schreibt run-scope.txt.
  Input:    CSV00-root.resolved.txt

  Fehler:   Abbruch wenn kein Modell matcht.
  Besonder: Keine Verzeichniserstellung.

  Output:   03-stages/run-scope.txt (ueberschrieben)

  ACHTUNG:  CSV04 ueberschreibt run-scope.txt vollstaendig.
            Die manuelle run-scope.txt (mit MASTER/BPMN Eintraegen)

  CSV08 - properties2csv.py
--------------------------------------------------------------

            in properties.csv.
            Owner ID wird gegen elements/relations.csv validiert.
  Input:    CSV00-root.resolved.txt
            run-scope.txt (SOURCE=XLSX Eintraege)

  Besonder: Nur SOURCE=XLSX - kein Fallback/Discovery.

--------------------------------------------------------------
  CSV09 - masterXml2Csv.py
--------------------------------------------------------------
  Zweck:    Konvertiert master.xml in CSV Import-Dateien.
            Unterstuetzt zwei sourceSystem-Typen in master.xml:
            "archi" und "bpmn" (als direkte Kinder von <master>)
  Input:    CSV00-root.resolved.txt
            run-scope.txt (SOURCE=MASTER, SOURCE=BPMN)
            02-artifacts/00-xml/00-master/master.xml
            02-artifacts/00-xml/01-mapping/bpmnmastercsvsync.txt
  Output:   02-artifacts/02-csv/00-master/ (OVERWRITE fuer archi)
            02-artifacts/02-csv/00-master/ (APPEND fuer bpmn)
            03-stages/99-logs/CSV09-masterXml2Csv.log

  master.xml Struktur:
    <master last-updated="..." last-updated-by="...">
      <a:element sourceSystem="archi" sourceModel="..." .../>
      <bpmn:definitions>
        <bpmn:process id="..." name="..." sourceSystem="bpmn"/>
      </bpmn:definitions>
      ...
    </master>

  Dispatcher-Logik:
    Iteriert direkte Kinder von <master>:
    - sourceSystem="archi" + Tag=element -> ArchiMate Parser
    - Tag=definitions (BPMN NS)          -> BPMN Parser
    - Unbekannt                          -> Log + Skip

  Scope-Filter (run-scope.txt):
    SOURCE=MASTER -> filtert archi Kinder nach sourceModel
    SOURCE=BPMN   -> wird in master.xml NICHT als Filter
                     verwendet (BPMN definitions haben kein
                     sourceModel am definitions-Tag selbst,
                     nur am inneren process-Tag)
    Leerer Scope  -> alle Kinder werden verarbeitet

  BPMN Match-Logik (pro process Element):
    1. Name-Match (exakt, case-sensitive) gegen elements.csv
       MATCH    -> Property Row: archi_id, BPMN_ID, <bpmn_id>
       NO MATCH -> Neues Element ohne ID (Archi vergibt beim
                   Import) + Property Row: (leer), BPMN_ID, <bpmn_id>
    2. Within-Run Deduplication:
       Bereits geschriebene Namen werden in-memory gemerkt
       sodass mehrere BPMN Blocks im selben Run keine
       Duplikate erzeugen.

  Namespace-Handling:
    BPMN Tags werden per local-name gematcht (namespace-Strip).
    Funktioniert mit allen BPMN Namespace-Varianten:
    BPMN 2.0, Camunda, Flowable, Activiti etc.

  Schreibverhalten:
    ArchiMate Path: OVERWRITE (atomic via Buffer)
    BPMN Path:      APPEND-ONLY

--------------------------------------------------------------
  CSV99 - export_snapshot.py
--------------------------------------------------------------
  Zweck:    Erstellt einen bereinigten Import-Snapshot aus
            den Master CSVs fuer den Archi CSV Import.
            Master CSVs werden NIE veraendert.
  Input:    CSV00-root.resolved.txt
            02-artifacts/02-csv/00-master/*.csv
            02-artifacts/02-csv/02-sync/csvexport.txt
  Output:   02-artifacts/02-csv/04-import/*.csv (overwrite)
            03-stages/99-logs/CSV99-export_snapshot.log

  Verarbeitungslogik pro Datei:
    elements.csv:
      Key = ID (wenn vorhanden) oder (Type, Name, Doc, Spec)
      Last-wins Deduplication
      Type-Exclusion via csvexport.txt

    properties.csv:
      Key = (ID, Key-Spalte) oder (Key-Spalte, Value)
      Last-wins Deduplication

    relations.csv:
      Key = (Type, Source, Target, Specialization)
      Last-wins Deduplication

  Besonder: ID-lose Elemente (BPMN Stubs) werden unterstuetzt.
            csvexport.txt filtert Typen (kein Regex, exakt).
            Aktuell aktive Exclusion: ArchimateModel

==============================================================
  7. RUN-SCOPE.TXT KONVENTION (DETAIL)
==============================================================

  Pair-Regeln:
    1. SOURCE= und MODEL= stehen auf aufeinanderfolgenden Zeilen
    2. Kein Leerzeichen oder Blank zwischen den Zeilen
    3. Ein Pair ist aktiv wenn BEIDE Zeilen NICHT mit # beginnen
    4. Ein Pair ist inaktiv wenn EINE ODER BEIDE Zeilen mit # beginnen
    5. SNAPSHOT_SOURCE= und SNAPSHOT_MODEL= sind eigene Schluessel
       und werden nie als SOURCE/MODEL gematcht

  Aktuelle bekannte SOURCE-Typen:
    archi    .archimate Modelle (CSV01/CSV03)
    OEF      OEF XML Exporte (CSV04 Inventar)
    XLSX     Excel Exporte (CSV07/CSV08)
    CSV      CSV Exporte (CSV04 Inventar)
    MASTER   Fuer master.xml Run relevant (CSV09)
    BPMN     BPMN Modelle im Flow (CSV09)

  Beispiel einer vollstaendigen run-scope.txt:

    SOURCE=archi
    MODEL=Importer.archimate
    #SOURCE=archi
    #MODEL=InaktivesModell.archimate
    SOURCE=OEF
    MODEL=Importer.xml
    SOURCE=MASTER
    MODEL=Importer.xml
    SOURCE=BPMN
    MODEL=Business Process.bpmn
    # SNAPSHOT_START
    #SNAPSHOT_SOURCE=archi
    #SNAPSHOT_MODEL=Importer.xml
    #SNAPSHOT_SOURCE=bpmn
    #SNAPSHOT_MODEL=BUP00-Modellieren.bpmn
    # SNAPSHOT_END

  Lese-Verhalten der Scripts:
    Jedes Script liest nur den SOURCE-Typ der fuer es relevant ist.
    CSV09 liest SOURCE=MASTER und SOURCE=BPMN.
    CSV07/08 lesen SOURCE=XLSX.
    CSV03 schreibt SOURCE=archi.
    Andere SOURCE-Typen werden von den jeweiligen Scripts ignoriert.

  TD-03: CSV09 BPMN Scope-Filter unvollstaendig

  Betrifft: CSV09, SOURCE=BPMN in run-scope.txt

  Fix:      Waere moeglich wenn sourceModel auf definitions-Tag
