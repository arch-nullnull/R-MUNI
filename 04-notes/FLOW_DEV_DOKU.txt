================================================================================
  1. KONZEPT & PHILOSOPHIE
================================================================================

FLOW ist ein schlanker, deterministischer Script-Orchestrator.
Er verbindet Modellwerkzeuge (Archi, Camunda) mit Python-Scripts
über eine rein konfigurationsgetriebene Triggerlogik.

Grundprinzip:
  Modell-Element  -->  Trigger-Erkennung  -->  Dispatch-Key
  Dispatch-Key    -->  Mapping            -->  Script-Dateiname
  Script-Dateiname-->  Ausführung         -->  Ergebnis

FLOW tut NICHT:
  - Prozesse interpretieren
  - Diagramme verstehen
  - Engine-Semantik abbilden (kein BPMN-Runner, kein Workflow-Engine)
  - Entscheidungslogik ausführen

FLOW tut NUR:
  - XML scannen
  - konfigurierte Muster erkennen (Trigger)
  - gemappte Scripts in definierter Reihenfolge starten

Designziel:
  Konfiguration fuer das WAS  –  Code fuer das WIE.

  Was als Trigger gilt, welche Bedingungen erfuellt sein muessen und
  welchen Dispatch-Key ein Element liefert: alles extern in .txt-Dateien.
  Was "Archi-Property-Indirektion" bedeutet oder wie ein BPMN-Tag
  geparst wird: bleibt als Engine-Code in flow.py, aendert sich aber
  nur bei neuen XML-Quell-Formaten.

  4. ARCHITEKTURÜBERSICHT
================================================================================

  Statische Sicht (Dateien & Abhaengigkeiten):

    +---------------------+     liest      +--------------------+
    |   flowtriggers.txt  |<---------------| flow.py            |
    +---------------------+                | flowdiscover.py    |
                                           +--------------------+
    +---------------------+     liest      |
    |   flowmapping.txt   |<---------------|
    +---------------------+                |
                                           |
    +---------------------+     scannt     |
    |  00-xml/03-child/   |<---------------|
    |  *.xml *.bpmn ...   |                |
    +---------------------+                |
                                           |
    +---------------------+   startet      |
    |  01-scripts/*.py    |<---------------|
    +---------------------+


  Laufzeit-Ablauf flow.py (3 Phasen):

    Phase 1 – SCAN
    +--------------------------------------------------+
    | Alle XML-Dateien in 03-child rekursiv einlesen   |
    | Pro Datei: detect_triggers() aufrufen            |
    |   --> Archi-Engine oder BPMN-Engine              |
    |   --> Trigger-Dict mit order, key, section       |
    | Alle Trigger in all_triggers sammeln             |
    +--------------------------------------------------+
             |
             v
    Phase 2 – SORT
    +--------------------------------------------------+
    | all_triggers.sort(key=order)                     |
    | Garantierte Ausführungsreihenfolge               |
    | unabhaengig von Dateilage oder Dateisystem       |
    +--------------------------------------------------+
             |
             v
    Phase 3 – EXEC
    +--------------------------------------------------+
    | Pro Trigger: Dispatch-Key in flowmapping.txt     |
    | nachschlagen -> Script-Name                      |
    | Script mit subprocess ausfuehren                 |
    | Bei returncode != 0 --> ABORT                    |
    +--------------------------------------------------+


  Detection-Engines (innerhalb flow.py):

    detect_triggers()
         |
         +-- [source == "archi"] --> _detect_archi()
         |       |
         |       +-- _build_propdefs()   Archi Property-ID -> Name Map
         |       +-- _read_props()       Properties eines Elements lesen
         |       +-- _check_conditions() AND-Pruefung aller conditions
         |       +-- _resolve_dispatch_key()
         |
         +-- [source == "bpmn"]  --> _detect_bpmn()
                 |
                 +-- Kind-Tags direkt lesen (kein Indirektions-System)
                 +-- _check_conditions()
                 +-- _resolve_dispatch_key()


================================================================================
  5. DATEI: flowtriggers.txt
================================================================================

  Format: INI-Stil (Python configparser-kompatibel)
  Kommentare: # am Zeilenanfang oder inline nach Wert
  Kodierung: UTF-8

  ------------------------------------------------------------------------------
  5.1 Pflichtfelder pro Sektion
  ------------------------------------------------------------------------------

  [section_name]
    Eindeutiger Name der Regel. Beliebig waehlbar, empfohlen:
    <source>_<elementtyp>  z.B. archi_workpackage, bpmn_servicetask

  order = <ganzzahl>
    Bestimmt die globale Ausfuehrungsreihenfolge der durch diese Regel
    ausgeloesten Scripts. Niedrigere Zahl = frueher ausgefuehrt.
    Empfehlung: 10er-Schritte (10, 20, 30...) fuer spaeteres Einfuegen.
    Gleiche order-Werte: Reihenfolge untereinander undefiniert -> vermeiden.

  source = archi | bpmn
    Welche Detection-Engine verwendet wird.
    archi  -> Archi OEF 5.8 (Property-Indirektion via propertyDefinition)
    bpmn   -> BPMN 2.0 / Camunda 7 & 8 (direkte Kind-Tag-Auswertung)

  element_tag = <string>
    Lokaler XML-Tag-Name (Namespace-agnostisch).
    archi: immer "element"
    bpmn:  "serviceTask", "userTask", "sendTask", etc.

  condition.<n> = <condition-ausdruck>
    Mindestens eine Condition erforderlich. Alle Conditions AND-verknuepft.
    <n> ist beliebig (1, 2, a, b...) – nur zur Lesbarkeit, wird sortiert.
    Zwei Formate (siehe 5.3).

  dispatch_key = <dispatch-ausdruck>
    Woher der Schluessel kommt, der in flowmapping.txt nachgeschlagen wird.
    Zwei Formate (siehe 5.4).

  ------------------------------------------------------------------------------
  5.2 Optionale Felder
  ------------------------------------------------------------------------------

  element_type = <string>
    Nur fuer source=archi relevant.
    Wert des xsi:type-Attributs, der uebereinstimmen muss.
    Fehlt oder leer -> kein Filter auf xsi:type.

  ------------------------------------------------------------------------------
  5.3 Condition-Formate
  ------------------------------------------------------------------------------

  Fuer source=archi:

    condition.1 = property:<PropertyName>=<Wert>

    Prueft ob das Element eine Archi-Property mit dem angegebenen
    Namen und exakt dem angegebenen Wert besitzt.

    Beispiel:
      condition.1 = property:Trigger=Ja
      condition.2 = property:Status=Active

    Hinweis: Property-Aufloesung nutzt die propertyDefinition-Tabelle
    im XML-Dokument. Der Name ist der menschenlesbare Name, nicht die ID.

  Fuer source=bpmn:

    condition.1 = tag:<TagName>:<Enthält-Text>

    Prueft ob ein direktes Kind-Element des Tasks den angegebenen
    lokalen Tag-Namen hat UND dessen Textinhalt den gesuchten
    String enthaelt (Substring-Suche, keine Regex).

    Der <Enthält-Text> darf selbst Doppelpunkte enthalten –
    gesplittet wird nur beim ersten Doppelpunkt nach dem TagName.

    Beispiel:
      condition.1 = tag:documentation:Trigger:Ja
      (sucht Kind-Tag "documentation" mit Inhalt der "Trigger:Ja" enthaelt)

  ------------------------------------------------------------------------------
  5.4 Dispatch-Key-Formate
  ------------------------------------------------------------------------------

    dispatch_key = property:<PropertyName>
      Dispatch-Key ist der Wert einer Archi-Property.
      Beispiel: dispatch_key = property:Type

    dispatch_key = attr:<Attributname>
      Dispatch-Key ist der Wert eines XML-Attributs des Elements.
      Beispiel: dispatch_key = attr:id

  ------------------------------------------------------------------------------
  5.5 Vollstaendiges Beispiel
  ------------------------------------------------------------------------------

    [archi_workpackage]
    order           = 10
    source          = archi
    element_tag     = element
    element_type    = WorkPackage
    condition.1     = property:Trigger=Ja
    dispatch_key    = property:Type

    [bpmn_servicetask]
    order           = 20
    source          = bpmn
    element_tag     = serviceTask
    condition.1     = tag:documentation:Trigger:Ja
    dispatch_key    = attr:id

  ------------------------------------------------------------------------------
  5.6 Mehrere Bedingungen (AND)
  ------------------------------------------------------------------------------

    [archi_applicationprocess]
    order           = 30
    source          = archi
    element_tag     = element
    element_type    = ApplicationProcess
    condition.1     = property:Trigger=Ja
    condition.2     = property:Status=Active
    dispatch_key    = property:Type

    Beide conditions muessen zutreffen. Fehlt eine -> Element wird uebersprungen.

  ------------------------------------------------------------------------------
  5.7 Mehrere Sektionen desselben Typs
  ------------------------------------------------------------------------------

  Erlaubt und sinnvoll, wenn z.B. WorkPackage und ApplicationProcess
  beide als Trigger fungieren sollen:

    [archi_workpackage]
    order = 10
    ...

    [archi_applicationprocess]
    order = 20
    ...

  Jede Sektion wird unabhaengig ausgewertet.


================================================================================
  6. DATEI: flowmapping.txt
================================================================================

  Format: KEY=VALUE, eine Zeile pro Eintrag
  Kommentare: # am Zeilenanfang
  Kodierung: UTF-8

  Syntax:
    <Dispatch-Key>=<Script-Dateiname>

  Regeln:
    - Leerzeilen und #-Zeilen werden ignoriert
    - Schluessel muessen eindeutig sein (Duplikate -> ABORT)
    - Der Dateiname ist relativ zu 02-artifacts/01-scripts/
    - Leerzeichen um = werden getrimmt
    - Script-Dateinamen duerfen Leerzeichen enthalten

  Beispiel:
    Script=S00-validate root.py
    Activity_0xh630m=S00-validate root.py
    MyKey=S01-process data.py

  Hinweis:
    Die Reihenfolge der Eintraege in flowmapping.txt hat KEINEN
    Einfluss auf die Ausfuehrungsreihenfolge. Diese wird
    ausschliesslich durch "order" in flowtriggers.txt bestimmt.
    flowmapping.txt ist ein reines Lookup-Dict.


================================================================================
  7. DATEI: flow.py – DETAILDOKUMENTATION
================================================================================

  ------------------------------------------------------------------------------
  7.1 Einstiegspunkt & Log-Initialisierung
  ------------------------------------------------------------------------------

  main() startet mit einer Besonderheit:
  Der Log-Pfad muss vor dem ersten log()-Aufruf bekannt sein.
  Dafuer wird root.txt vorab mit _read_root_value() stille gelesen
  (ohne log()-Abhaengigkeit), um den Pfad zu 03-stages/99-logs/flow.log
  aufzubauen. Erst dann wird init_log() aufgerufen.

  Ablauf main():

    1. root.txt still lesen -> pre_root ermitteln
    2. init_log() -> flow.log oeffnen (append-Modus, Run-Header schreiben)
    3. resolve_blueprint_root() -> vollstaendige Validierung mit Logging
    4. Pfade aufbauen (xml_root, scripts_dir, mapping_file, triggers_file)
    5. load_mapping() laden
    6. load_trigger_rules() laden + nach order sortieren
    7. Phase 1: XML-Scan + Trigger-Sammlung
    8. Phase 2: Trigger nach order sortieren
    9. Phase 3: Scripts ausfuehren
    10. flow.log schliessen

  ------------------------------------------------------------------------------
  7.2 Funktion: _read_root_value(root_file)
  ------------------------------------------------------------------------------

  Zweck:    Liest nur BLUEPRINT_ROOT aus root.txt, ohne log() zu benoetigen.
            Wird vor init_log() aufgerufen um den Log-Pfad zu bestimmen.
  Parameter: root_file – absoluter Pfad zu root.txt
  Rueckgabe: String (Wert) oder None
  Fehler:   Keine Ausnahmen, kein abort() – stille Funktion

  ------------------------------------------------------------------------------
  7.3 Funktion: resolve_blueprint_root()
  ------------------------------------------------------------------------------

  Zweck:    Ermittelt BLUEPRINT_ROOT vollstaendig und validiert das Ergebnis.
            Unterstuetzt absolute und relative Pfadangaben in root.txt.
  Verhalten:
    - Sucht root.txt zwei Ebenen ueber flow.py (../../root.txt)
    - Prueft auf doppelte BLUEPRINT_ROOT-Eintraege -> ABORT
    - Loest relative Pfade relativ zum Verzeichnis von root.txt auf
    - Prueft ob das Verzeichnis existiert -> ABORT wenn nicht

  root.txt Format:
    # Kommentar
    BLUEPRINT_ROOT=C:\Prototyping\Modelle\Archi\Blueprint
    oder relativ:
    BLUEPRINT_ROOT=..\..\Blueprint

  ------------------------------------------------------------------------------
  7.4 Funktion: load_mapping(path)
  ------------------------------------------------------------------------------

  Zweck:    Laedt flowmapping.txt in ein dict.
  Validierung:
    - Datei muss existieren
    - Jede nicht-Kommentar-Zeile muss ein "=" enthalten
    - Schluessel und Wert duerfen nicht leer sein
    - Keine doppelten Schluessel
  Rueckgabe: dict  { dispatch_key -> script_filename }

  ------------------------------------------------------------------------------
  7.5 Funktion: load_trigger_rules(path)
  ------------------------------------------------------------------------------

  Zweck:    Laedt flowtriggers.txt via configparser.
            Parst und validiert alle Sektionen.
            Sortiert Regeln nach order.
  Rueckgabe: list of rule-dicts

  Rule-Dict Struktur:
    {
      "section":      str,      # Sektionsname
      "order":        int,      # Ausfuehrungsreihenfolge
      "source":       str,      # "archi" | "bpmn"
      "element_tag":  str,      # lokaler XML-Tag
      "element_type": str|None, # xsi:type Filter (None = kein Filter)
      "conditions":   list,     # Liste von condition-dicts
      "dispatch_key": dict,     # dispatch-key-dict
    }

  Condition-Dict Archi:
    { "kind": "property", "name": str, "value": str }

  Condition-Dict BPMN:
    { "kind": "tag", "tag": str, "contains": str }

  Dispatch-Key-Dict:
    { "kind": "property"|"attr", "name": str }

  ------------------------------------------------------------------------------
  7.6 Funktion: detect_triggers(root, rules)
  ------------------------------------------------------------------------------

  Zweck:    Wendet alle Regeln auf einen XML-Root an.
            Baut propdefs einmalig pro Datei (wenn Archi-Regeln vorhanden).
  Rueckgabe: list of trigger-dicts

  Trigger-Dict Struktur:
    {
      "source":  str,   # "archi" | "bpmn"
      "section": str,   # Sektionsname der matchenden Regel
      "order":   int,   # uebernommen aus der Regel
      "key":     str,   # der aufgeloeste Dispatch-Key
      "info":    str,   # Archi: identifier / BPMN: name-Attribut
    }

  ------------------------------------------------------------------------------
  7.7 Archi Property-Indirektion (warum so komplex?)
  ------------------------------------------------------------------------------

  In Archi OEF 5.8 sind Properties NICHT direkt am Element gespeichert.
  Stattdessen gibt es im XML-Dokument eine zentrale Tabelle:

    <propertyDefinition identifier="propid-001">
      <name>Trigger</name>
    </propertyDefinition>

  Und am Element nur ein Referenz:

    <property propertyDefinitionRef="propid-001">
      <value>Ja</value>
    </property>

  _build_propdefs() baut die Map:  propid-001 -> "Trigger"
  _read_props()     liest:         element -> { "Trigger": "Ja", ... }

  Ohne diese Indirektion waere ein direkter Vergleich auf den
  Property-Namen nicht moeglich. Das ist der Hauptunterschied
  zur BPMN-Engine und der Grund warum Archi einen eigenen Detector hat.

  ------------------------------------------------------------------------------
  7.8 Funktion: _check_conditions(conditions, props, tag_contents)
  ------------------------------------------------------------------------------

  AND-Verknuepfung aller Conditions.
  Gibt False zurueck sobald eine Bedingung nicht erfuellt ist (short-circuit).
  props und tag_contents sind optional – fehlt das passende Dict zur
  condition.kind -> False (sicheres Fallback).

  ------------------------------------------------------------------------------
  7.9 Funktion: run_script(script_path, cwd)
  ------------------------------------------------------------------------------

  Startet das Script als Subprocess mit demselben Python-Interpreter
  (sys.executable) der auch flow.py ausfuehrt.
  cwd wird auf BLUEPRINT_ROOT gesetzt -> Scripts koennen relative
  Pfade ab Blueprint-Root verwenden.
  returncode != 0 -> ABORT (kein weiteres Script wird gestartet).

  ------------------------------------------------------------------------------

================================================================================
  8. DATEI: flowdiscover.py – DETAILDOKUMENTATION
================================================================================

  flowdiscover.py ist ein eigenstaendiges Diagnose-Tool.
  Es importiert NICHTS aus flow.py – vollstaendig standalone.

  Zweck:
    Vor dem Schreiben von Trigger-Regeln in flowtriggers.txt
    sehen, welche XML-Typen und Tags ueberhaupt im Scan-Ordner
    vorhanden sind – und ob sie bereits konfiguriert sind.

  ------------------------------------------------------------------------------
  8.1 Was wird gescannt
  ------------------------------------------------------------------------------

  Archi-Dateien:
    Alle <element>-Tags -> xsi:type-Attribut wird extrahiert.
    -> "element_type"-Kandidaten fuer flowtriggers.txt

  BPMN-Dateien:
    Alle Tags die Task, Event, Gateway, SubProcess, CallActivity
    oder AdHocSubProcess im Namen enthalten.
    Struktur-Tags (sequenceFlow, laneSet, etc.) werden gefiltert.
    -> "element_tag"-Kandidaten fuer flowtriggers.txt

  Erkennung ob Archi oder BPMN:
    is_archi(): prueft ob propertyDefinition oder model-Tag existiert
    is_bpmn():  prueft ob definitions, process, serviceTask etc. existiert
    Eine Datei kann beide liefern (theoretisch).

  ------------------------------------------------------------------------------
  8.2 Trigger-Matching
  ------------------------------------------------------------------------------

  Jeder gefundene Typ / Tag wird gegen flowtriggers.txt geprueft:

  match_archi_type(xtype, rules):
    Matcht wenn: source==archi UND (element_type==xtype ODER element_type leer)

  match_bpmn_tag(tag, rules):
    Matcht wenn: source==bpmn UND element_tag==tag

  Ausgabe pro Typ:
    CONFIGURED   -> section, order, dispatch_key werden angezeigt
    NOT CONFIGURED -> Hinweis dass keine Regel existiert

  ------------------------------------------------------------------------------
  8.3 Ausgabedateien
  ------------------------------------------------------------------------------

  flowdiscover.log  (03-stages/99-logs/)
    Detailliert. Pro Typ/Tag:
      - Trigger match: CONFIGURED / NOT CONFIGURED + Details
      - Found in: Liste der Dateipfade
      - Identifiers: bis zu 10 Archi-Element-IDs als Kontext
    Wird bei jedem Run neu geschrieben (kein append).

  flowdiscover.txt  (03-stages/)
    Kompakt. Direkt als Schreibhilfe fuer flowtriggers.txt nutzbar.
    Beispiel:
      element_type = WorkPackage    # 2 file(s) | CONFIGURED -> [archi_workpackage] order=10 ...
      element_type = ApplicationProcess  # 1 file(s) | NOT CONFIGURED
      element_tag  = serviceTask    # 3 file(s) | CONFIGURED -> [bpmn_servicetask] order=20 ...

  Konsole:
    Zusammenfassung + direkte Ausgabe aller NOT CONFIGURED Typen/Tags.

  ------------------------------------------------------------------------------
  8.4 Typischer Arbeitsablauf mit flowdiscover
  ------------------------------------------------------------------------------

    1. Neue XML-Dateien in 03-child ablegen
    2. flowdiscover.py ausfuehren
    3. flowdiscover.txt pruefen:
       -> Welche Typen sind "NOT CONFIGURED"?
       -> Diese in flowtriggers.txt als neue Sektion anlegen
    4. flowmapping.txt um den neuen Dispatch-Key erganzen
    5. flow.py ausfuehren
    6. flow.log pruefen


================================================================================
  9. LAUFZEITVERHALTEN & PHASEN
================================================================================

  Phase 1 – SCAN
  --------------
  Rekursiver os.walk() ueber 02-artifacts/00-xml/03-child.
  Innerhalb jedes Ordners alphabetische Dateireihenfolge (sorted(files)).
  Ueber Unterordner hinweg: keine garantierte Reihenfolge.
  -> Deshalb ist Phase 2 (order-Sort) zwingend notwendig.

  Akzeptierte Dateiendungen: .xml  .bpmn  .archimate
  Nicht-parsbare XML-Dateien -> ABORT

  Pro Datei wird detect_triggers() aufgerufen.
  Alle gefundenen Trigger werden in all_triggers gesammelt.
  Ein Trigger enthaelt den order-Wert seiner Regel.

  Phase 2 – SORT
  --------------
  all_triggers.sort(key=lambda t: t["order"])
  Garantiert die Ausfuehrungsreihenfolge unabhaengig von:
    - Dateisystem-Sortierung
    - Unterordner-Lage der XML-Dateien
    - Reihenfolge der Sektionen in flowtriggers.txt

  Phase 3 – EXEC
  --------------
  Lineare Iteration ueber sortierte Trigger-Liste.
  Pro Trigger:
    1. Dispatch-Key in flowmapping.txt nachschlagen
    2. Nicht gefunden -> SKIP (kein Abbruch, nur Log-Eintrag)
    3. Script-Pfad aufbauen und pruefen -> nicht gefunden -> ABORT
    4. subprocess.run([sys.executable, script_path], cwd=BLUEPRINT_ROOT)
    5. returncode != 0 -> ABORT

  Derselbe Dispatch-Key kann mehrfach in der Trigger-Liste vorkommen
  (mehrere XML-Dateien, gleiches Element). Das Script wird dann
  mehrfach ausgefuehrt – eines pro Treffer.


================================================================================
  10. LOGGING
================================================================================

  flow.log
  --------
  Pfad:     BLUEPRINT_ROOT/03-stages/99-logs/flow.log
  Modus:    append (akkumulierend ueber mehrere Runs)
  Trennmark pro Run:
              ============================================================
              FLOW Run: YYYY-MM-DD HH:MM:SS
              ============================================================

  Format jeder Zeile:
    [FLOW] YYYY-MM-DD HH:MM:SS | <Message>

  Wichtige Meldungstypen:
    Blueprint root resolved: <pfad>
    Loaded N mapping entries
    Loaded N trigger rule(s) from flowtriggers.txt (order: ...)
    SCAN: <relativer-pfad>
      TRIGGER [order=N] [section] key=... info=...
    Detected N trigger(s)
    Execution order: key1(order=10), key2(order=20)
    SKIP (unmapped): key=... [section]
    EXEC: <absoluter-script-pfad>
    FLOW finished: executed=N, total_triggers=N
    Log written to: <pfad>
    ABORT: <grund>

  flowdiscover.log
  ----------------
  Pfad:     BLUEPRINT_ROOT/03-stages/99-logs/flowdiscover.log
  Modus:    ueberschreibend (jeder Run neu)

  flowdiscover.txt
  ----------------
  Pfad:     BLUEPRINT_ROOT/03-stages/flowdiscover.txt
  Modus:    ueberschreibend (jeder Run neu)


================================================================================
  11. FEHLERBEHANDLUNG & ABBRUCHVERHALTEN
================================================================================

  abort(msg) loggt den Grund und beendet mit sys.exit(1).
  Der log-Handle wird vor dem Exit geschlossen.

  Abbruchgruende:

    root.txt nicht gefunden
      -> flow.py liegt falsch oder root.txt fehlt

    multiple BLUEPRINT_ROOT entries found
      -> root.txt enthaelt mehr als einen BLUEPRINT_ROOT-Eintrag

    BLUEPRINT_ROOT missing or empty
      -> root.txt vorhanden aber kein Eintrag oder Leerzeile

    resolved BLUEPRINT_ROOT does not exist
      -> Pfad in root.txt zeigt auf nicht existierendes Verzeichnis

    flowmapping.txt not found
      -> Datei fehlt im 04-flow Ordner

    invalid mapping line N: <zeile>
      -> Zeile ohne "=" in flowmapping.txt

    duplicate mapping key: <key>
      -> Dispatch-Key kommt mehrfach in flowmapping.txt vor

    flowtriggers.txt not found
      -> Datei fehlt im 04-flow Ordner

    [section] order is required
      -> order-Feld fehlt in einer Sektion

    [section] order must be an integer
      -> order-Wert ist keine Ganzzahl

    [section] source must be 'archi' or 'bpmn'
      -> ungueltige source-Angabe

    [section] element_tag is required
      -> element_tag fehlt in einer Sektion

    [section] at least one condition.<n> is required
      -> keine einzige condition in einer Sektion

    [section] dispatch_key is required / unknown format
      -> dispatch_key fehlt oder hat ungueltiges Format

    invalid XML: <datei> (<fehler>)
      -> XML-Datei nicht parsbar

    mapped script not found: <pfad>
      -> Mapping zeigt auf nicht existierendes Script

    script failed: <pfad>
      -> Script hat mit returncode != 0 beendet

  SKIP (kein Abbruch):
    Dispatch-Key nicht in flowmapping.txt gefunden.
    -> Trigger wird ignoriert, naechster wird verarbeitet.


================================================================================
  12. ERWEITERUNG: NEUE TRIGGER-REGEL HINZUFÜGEN
================================================================================

  Szenario: Neues Archi-Element "ApplicationProcess" soll als
  Trigger fungieren, wenn Trigger=Ja UND Status=Active gesetzt ist.

  Schritt 1: flowdiscover.py ausfuehren
    -> Pruefen ob ApplicationProcess in flowdiscover.txt erscheint
    -> Sicherstellen dass element_type = ApplicationProcess vorhanden ist

  Schritt 2: flowtriggers.txt erweitern
    Neue Sektion hinzufuegen:

    [archi_applicationprocess]
    order           = 30
    source          = archi
    element_tag     = element
    element_type    = ApplicationProcess
    condition.1     = property:Trigger=Ja
    condition.2     = property:Status=Active
    dispatch_key    = property:Type

  Schritt 3: flowmapping.txt pruefen
    Den Dispatch-Key (Wert der Property "Type" am Element) als
    Eintrag ergaenzen falls noch nicht vorhanden:

    MeinApKey=S02-process application.py

  Schritt 4: flow.py ausfuehren und flow.log pruefen
    -> TRIGGER [order=30] [archi_applicationprocess] key=MeinApKey ...
    -> EXEC: ...S02-process application.py

  Kein Eingriff in flow.py oder flowdiscover.py noetig.


================================================================================
  13. ERWEITERUNG: NEUE XML-QUELLE (NEUE SOURCE-ENGINE)
================================================================================

  Wenn eine neue XML-Quelle (z.B. eine proprietaere App) hinzukommt
  deren Struktur sich von Archi und BPMN unterscheidet, genuegt
  die Konfiguration alleine nicht mehr.

  In flow.py muessen folgende Stellen erweitert werden:

  A) detect_triggers():
     Neue elif-Bedingung ergaenzen:

       elif rule["source"] == "xyapp":
           triggers.extend(_detect_xyapp(root, rule))

  B) Neue Funktion _detect_xyapp() implementieren:
     Analog zu _detect_archi() oder _detect_bpmn().
     Gibt list of trigger-dicts zurueck (mit order, key, section, info).

  C) load_trigger_rules():
     source-Validierung erweitern:

       if source not in ("archi", "bpmn", "xyapp"):

  D) flowtriggers.txt:
     Neue Sektionen mit source=xyapp anlegen.

  Warum ist dieser Code-Eingriff unvermeidbar?
    Weil jede Quelle eine eigene XML-Navigationslogik benoetigt.
    Archi hat Property-Indirektion (propertyDefinition-Tabelle).
    BPMN liest direkte Kind-Tags.
    Eine neue Quelle koennte z.B. Attribute, Namespaces oder
    verschachtelte Strukturen anders verwenden.
    Diese strukturelle Verschiedenheit ist nicht konfigurierbar –
    sie ist Algorithmus.

  Designprinzip beibehalten:
    Der Code-Eingriff beschraenkt sich auf die Engine-Ebene.
    Welche Elemente aus der neuen Quelle als Trigger fungieren,
    welche Bedingungen gelten und welchen Dispatch-Key sie liefern:
    das bleibt vollstaendig in flowtriggers.txt konfigurierbar.


================================================================================
  14. BEKANNTE EINSCHRÄNKUNGEN
================================================================================

  Kein Parallel-Aufruf
    flow.py ist nicht fuer parallele Ausfuehrung ausgelegt.
    Mehrere gleichzeitige Instanzen schreiben in dasselbe flow.log
    (append-Modus) ohne Locking -> Log-Eintraege koennen sich mischen.

  Kein Rollback
    Schlaegt Script N fehl (ABORT), werden Scripts N+1 bis Ende
    nicht ausgefuehrt. Es gibt kein automatisches Rueckgaengigmachen
    der bereits abgeschlossenen Scripts.

  Gleiche order-Werte
    Zwei Trigger mit identischem order-Wert: ihre relative Reihenfolge
    zueinander ist undefiniert (abhaengig von Python sort-Stabilitaet
    und Scan-Reihenfolge). Vermeiden durch eindeutige order-Werte.

  Kondition-Typ "property" nur fuer Archi
    Das "property:"-Format in condition.<n> funktioniert nur bei
    source=archi, weil nur dort _read_props() aufgerufen wird.
    Bei source=bpmn wird props=None uebergeben -> condition schlaegt
    immer fehl. Kein Fehler, aber stille Nicht-Erkennung.

  Dateiendungen
    Nur .xml, .bpmn, .archimate werden verarbeitet.
    Andere Endungen werden ohne Warnung uebersprungen.

  Python-Version
    Verschachtelte f-strings (f"...{f'...'}...") sind erst ab
    Python 3.12 erlaubt. Der Code vermeidet diese Konstrukte
    fuer Kompatibilitaet ab Python 3.8.


================================================================================
  15. GLOSSAR
================================================================================

  Archi OEF
    Open Exchange Format 5.8 – XML-Exportformat von Archi (ArchiMate-Tool).
    Eigenschaften von Elementen werden ueber eine propertyDefinition-Tabelle
    und propertyDefinitionRef indirekt referenziert.

  BPMN 2.0
    Business Process Model and Notation – XML-Standard fuer Prozessmodelle.
    Camunda 7 und 8 exportieren in diesem Format (.bpmn).

  Blueprint Root (BLUEPRINT_ROOT)
    Das Wurzelverzeichnis des gesamten Blueprint-Projekts.
    Wird aus root.txt aufgeloest. Alle anderen Pfade sind relativ dazu.

  Condition
    Eine einzelne Pruefbedingung innerhalb einer Trigger-Regel.
    Mehrere Conditions sind AND-verknuepft.

  Dispatch-Key
    Der Schluessel, der nach erfolgreicher Trigger-Erkennung aus dem
    XML-Element extrahiert wird und in flowmapping.txt nachgeschlagen
    wird um den Script-Namen zu ermitteln.

  Detection-Engine
    Der Python-Code-Block der weiss, wie eine bestimmte XML-Quelle
    (Archi, BPMN, ...) durchsucht werden muss. Implementiert als
    _detect_archi() bzw. _detect_bpmn() in flow.py.

  order
    Ganzzahliger Wert pro Trigger-Regel in flowtriggers.txt.
    Bestimmt die globale Ausfuehrungsreihenfolge aller Scripts,
    unabhaengig davon in welcher Datei oder welchem Unterordner
    der Trigger gefunden wurde.

  propertyDefinition
    XML-Element in Archi OEF das eine Property-ID auf einen
    menschenlesbaren Namen mappt. Wird von _build_propdefs() gelesen.

  Section
    Ein benannter Block in flowtriggers.txt, eingeleitet durch [name].
    Repraesentiert eine einzelne Trigger-Erkennungsregel.

  Trigger
    Ein XML-Element das alle konfigurierten Bedingungen einer Regel erfuellt.
    Resultiert in einem Dispatch-Key und bei erfolgreichem Mapping
    in der Ausfuehrung eines Scripts.

  xsi:type
    XML-Attribut (Namespace http://www.w3.org/2001/XMLSchema-instance)
    das den Untertyp eines XML-Elements angibt.
    In Archi OEF z.B. "WorkPackage", "ApplicationProcess" usw.
    Wird Namespace-agnostisch ueber get_xsi_type() gelesen.
