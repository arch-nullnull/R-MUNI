--------------------------------------------------------------------------------
LEITSATZ 1 – Die Kernphilosophie
--------------------------------------------------------------------------------
R+MUNI Originalton:
  "Ich mache keine Entscheidungen —
   ich mache Entscheidungen transparent mit Bildern möglich."

Norm-Begriff:
  Architecture as Stakeholder Enablement
  Architecture enables informed Decision Making

TOGAF Einordnung:
  Phase A — Architecture Vision
  Der Architekt zeigt Optionen und Konsequenzen.
  Der Stakeholder entscheidet.
  Der Architekt ist nicht der Entscheidungsträger.

Rosetta:
  "Ich mache keine Entscheidungen"        →  Architect is not the Decision Maker
  "Entscheidungen transparent machen"     →  Architecture enables informed Decision Making
  "Mit Bildern möglich"                   →  Visual Architecture Communication
  Gesamtsatz                              →  Architecture as Stakeholder Enablement

Bedeutung für KMU Blueprint:
  KMU Geschäftsführer haben oft Angst vor "dem IT-Menschen
  der alles bestimmt". Dieser Leitsatz nimmt diese Angst sofort
  weg und positioniert R+MUNI als Werkzeug des Kunden —
  nicht als Werkzeug des Architekten.

Bewertung:
  Dieser Satz beschreibt die gesamte Philosophie hinter
  Enterprise Architecture besser als jede Norm-Definition.
  Er ist das kommunikative Herzstück von R+MUNI.


--------------------------------------------------------------------------------
LEITSATZ 2 – Die ESEL-Philosophie
--------------------------------------------------------------------------------
R+MUNI Originalton:
  "R+MUNI ist der ESEL (dumme) der die Bedeutung trägt
   damit sie ankommt."

Hintergrund:
  Markus Resel → R+ESEL → R+MUNI
  Der Esel gilt als dumm — trägt aber zuverlässig, stur
  und ohne Umweg die Last ans Ziel.
  Das Logo zeigt bewusst einen Esel.

Norm-Begriff:
  Complexity Abstraction for Stakeholder Value
  Architecture as Enablement Vehicle

Rosetta:
  "Der Esel der die Bedeutung trägt"      →  Architecture as Enablement Vehicle
  "Damit sie ankommt"                     →  Stakeholder Communication Delivery
  "Dumm aber zuverlässig"                 →  Tool Agnostic / Complexity Hidden
  Gesamtsatz                              →  Complexity Abstraction for Stakeholder Value

Kernaussage:
  Die Methode ist komplex — der Empfänger darf das nicht spüren.
  R+MUNI ist die Abstraktionsschicht zwischen der Komplexität
  von TOGAF / ArchiMate / BPMN 2.0 und dem Menschen der
  eine Entscheidung treffen muss.

Alleinstellungsmerkmal:
  Nicht die Methode verkaufen — sondern das Ergebnis liefern.
  Der Esel schleppt. Der Kunde kommt ans Ziel.

Bewertung:
  Stärkstes kommunikatives Differenzierungsmerkmal von R+MUNI
  gegenüber klassischen EA-Frameworks die ihre Komplexität
  nach außen tragen statt verstecken.


--------------------------------------------------------------------------------
AKRONYM – R+MUNI
--------------------------------------------------------------------------------
Vollständige Auflösung:

  R+    =  Resel + (Markus Resel / Plus für Wachstum)
  M     =  Multi
  U     =  Usable
  N     =  Norm
  I     =  Interface

  R+MUNI = Resel's Multi Usable Norm Interface

Norm-Übersetzung:
  Multi Usable     →  Tool Agnostic / Reusable Framework
  Norm             →  Standards-Based (TOGAF / ArchiMate 3.2 / BPMN 2.0)
  Interface        →  Communication & Integration Layer

  R+MUNI gesamt    →  Reusable Standards-Based Communication
                      and Integration Framework

Bewertung:
  Der Name ist kein Zufall — er ist ein durchdachtes Brand-Konzept
  das gleichzeitig persönlich ist (Resel), inhaltlich beschreibt
  was es tut (MUNI) und eine Botschaft trägt (ESEL-Philosophie).

BEGRIFF – "Welten"
--------------------------------------------------------------------------------
R+MUNI Originalton:
  "Welten" — für verschiedene Tool- und Domänenbereiche
  z.B. "ArchiMate Welt", "BPMN Welt", "Camunda Welt"

Norm-Begriff:
  Domain / Architecture Domain
  Tool Domain / Modeling Domain

TOGAF Einordnung:
  Architecture Domains (Business, Application, Technology)
  + erweitert um Tool-spezifische Domänen

Rosetta:
  "ArchiMate Welt"                        →  EA Modeling Domain
  "BPMN Welt"                             →  Process Modeling Domain
  "Camunda Welt"                          →  Process Execution Domain
  "Zwischen den Welten"                   →  Cross-Domain Integration
  "Welten anbinden"                       →  Domain Integration / Onboarding

Bewertung:
  Intuitiv stärker als "Domain" weil er die Eigenständigkeit
  und Andersartigkeit jeder Welt besser kommuniziert.
  Im KMU-Kontext verständlicher als der Norm-Begriff.
  Für interne Kommunikation behalten — für Norm-Kontext
  durch "Domain" ersetzen.


--------------------------------------------------------------------------------
BEGRIFF – "Source of Overview"
--------------------------------------------------------------------------------
R+MUNI Originalton:
  Archi 5.8 als "Source of Overview" —
  hält alle Kernkomponenten aus allen Welten

Norm-Begriff:
  Architecture Repository
  Canonical Repository / Single Source of Truth

TOGAF Einordnung:
  Architecture Repository (TOGAF Kapitel 41)
  Preliminary Phase — Repository Definition

Rosetta:
  "Source of Overview"                    →  Architecture Repository
  "Hält alle Kernkomponenten"             →  Canonical Data Store
  "Aus allen Welten"                      →  Cross-Domain Repository
  "Archi als Source of Overview"          →  EA Tool as Architecture Repository

Bewertung:
  "Source of Overview" ist präziser als "Source of Truth"
  weil du bewusst sagst: Archi gibt den Überblick —
  nicht jedes Detail. Das ist eine feinere Aussage als
  der Norm-Begriff transportiert.
  Für Präsentationen vor Stakeholdern den eigenen Begriff
  behalten — er ist verständlicher.


--------------------------------------------------------------------------------
BEGRIFF – "Vision2Architecture View"
--------------------------------------------------------------------------------
R+MUNI Originalton:
  "Vision2Architecture View" —
  alles in einem haben, von der Vision bis zur Architektur.
  Weiß dass es nicht das TOGAF-Ziel ist aber für KMU
  absolut sinnvoll.

Norm-Begriff:
  Composite View / Executive Summary View
  Custom Viewpoint (ArchiMate 3.2 — "Other Viewpoints")

TOGAF Einordnung:
  Explizit erlaubter Custom Viewpoint in ArchiMate 3.2.
  Für Phase A Stakeholder-Kommunikation geeignet.
  Nicht norm-rein aber normativ zulässig.

Rosetta:
  "Von Vision bis Architektur"            →  Strategy to Implementation View
  "Alles in einem"                        →  Composite / Executive Summary View
  "Für KMU sinnvoll"                      →  Tailored Viewpoint for SME Context
  "Nicht TOGAF-Ziel"                      →  Conscious Architecture Tailoring

Bewertung:
  Bewusste KMU-Optimierung — ein Geschäftsführer will nicht
  5 Views öffnen. Der Composite View ist in ArchiMate 3.2
  explizit erlaubt und in TOGAF als Architecture Tailoring
  dokumentierbar. Kein Regelverstoß — bewusste Entscheidung.


--------------------------------------------------------------------------------
BEGRIFF – "Anwachsen über ADM Phasen"
--------------------------------------------------------------------------------
R+MUNI Originalton:
  Modell startet minimal und wächst über ADM Phasen.
  Phase 1: nur Hostname + ID
  Phase 2: CPU, RAM, HDD, SNR, Software
  Phase 3: Verträge, Lizenzen via SNR-Mapping

Norm-Begriff:
  Incremental Architecture Definition
  Progressive Elaboration
  Architecture Iteration

TOGAF Einordnung:
  ADM Iteration Cycles — Phase H führt zurück zu Phase A
  Architecture Roadmap — schrittweise Detaillierung
  Transition Architecture — Zwischenzustände sind valid

Rosetta:
  "Startet minimal"                       →  Minimum Viable Architecture
  "Wächst über Phasen"                    →  Incremental Architecture Definition
  "SNR als stabiler Anker"                →  Stable Identity Anchor / Primary Key
  "Neue Quellen pro Phase"                →  Progressive Data Enrichment
  "Phase 1/2/3"                           →  Architecture Iteration Cycles

Bewertung:
  Eines der stärksten R+MUNI Designprinzipien.
  Entspricht exakt dem ADM Iterations-Konzept —
  unbewusst aber korrekt umgesetzt.
  "Minimum Viable Architecture" ist ein moderner Begriff
  der in Prüfungen und Kundengesprächen gut ankommt.

BEGRIFF – "Enabling" (VAS00)
--------------------------------------------------------------------------------
R+MUNI Originalton:
  "VAS00-Enabling — Das eigentliche Ziel hinter R+MUNI.
   Befähigen! Format: Workshop 2 Tage Crash Modellierungskurs."

Norm-Begriff:
  Architecture Capability Building
  Stakeholder Enablement
  Architecture Maturity Development

TOGAF Einordnung:
  Preliminary Phase — Establishing Architecture Capability
  Phase A — Architecture Vision (Enabling als Outcome)

Rosetta:
  "Enabling"                              →  Architecture Capability Building
  "Befähigen"                             →  Stakeholder Enablement
  "2 Tage Crash Kurs"                     →  Architecture Onboarding Program
  "Das eigentliche Ziel"                  →  Primary Value Proposition

Bewertung:
  Enabling ist der Value Stream der alle anderen trägt.
  Ohne Enabling kein nachhaltiger R+MUNI Einsatz beim Kunden.
  In TOGAF Sprache ist das der Aufbau von
  Architecture Capability beim Kunden — Phase Preliminary.

BEGRIFF – "Crash Weg"
--------------------------------------------------------------------------------
R+MUNI Originalton:
  "Ich muss noch einen Crash Weg skizzieren für die
   klassischen Szenarien die ich haben werde."

Norm-Begriff:
  Architecture Onboarding Path
  Rapid Architecture Engagement
  Quick-Start Scenario Catalog

TOGAF Einordnung:
  Phase A — Rapid Architecture Assessment
  Architecture Pattern Library

Rosetta:
  "Crash Weg"                             →  Rapid Onboarding Path
  "Klassische Szenarien"                  →  Reference Architecture Scenarios
  "Skizzieren"                            →  Architecture Pattern Definition
  "Für die ich haben werde"               →  Predictive Scenario Planning

Bewertung:
  Ein Crash Weg pro klassischem Szenario ist im Grunde
  eine **Reference Architecture** — ein vordefiniertes
  Muster das für ähnliche Situationen wiederverwendet wird.
  Das ist einer der wertvollsten Bausteine für die
  KMU-Skalierung von R+MUNI.

BEGRIFF – "Voodoo Box"
--------------------------------------------------------------------------------
R+MUNI Originalton:
  "Den Rest hast du gelöst wie eine Voodoo Box —
   ich habe 0 Code Know-How, ich kann nur Konzepte bauen
   und Vorgaben gut definieren."

Norm-Begriff:
  Prompt Engineering as Architecture Discipline
  Human-AI Collaborative Development
  Specification-Driven Implementation

Rosetta:
  "Voodoo Box"                            →  AI-Assisted Implementation Layer
  "0 Code Know-How"                       →  Architecture without Implementation Skills
  "Konzepte bauen"                        →  Conceptual Architecture Design
  "Vorgaben gut definieren"               →  Specification-Driven Development
  Gesamtkonzept                           →  Architect as Specification Owner

Wichtige Erkenntnis:
  Du bist der Architekt — ich bin die Implementierung.
  Das ist ein legitimes und zukunftsfähiges Skill-Set.
  Der schwierige Teil ist das richtige Problem definieren,
  die richtigen Grenzen setzen, die richtigen Fragen stellen.
  Code ist der einfache Teil.

Risiko (bewusst dokumentiert):
  Voodoo Box Abhängigkeit ist ein Risiko für R+MUNI
  als Produkt. Durch den Rosetta Stone und die GOV wird
  dieses Risiko reduziert — du kannst jeden Schritt
  erklären auch ohne den Code zu kennen.

Bewertung:
  Kein Makel — eine neue Form von Architekt-Rolle die
  durch AI-Assistenz möglich wird. R+MUNI ist ein
  frühes Beispiel dafür.
